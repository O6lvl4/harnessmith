# harnessmith-run

ベンチ（`harnessmith.json` のあるフォルダ）で作業する。道具はベンチの `tool/harnessmith.py`。考え方は harnessmith-setup の `METHOD.md`。

## 守ること

- **解答と採点表を読まない。** `~/.harnessmith/<名前>/private/`、各試行の `score.json`・`score.md`・`judge/` を開かない。読んでよいのは `score_public.json`（部分ごとの点）、`events.jsonl`、`ledger.jsonl`、`notes/`、`comp/`。
- **構成の案を自分で書かない。** 案は振り返り役（`reflect`）に出させる。あなたは解答に触れていなくても、利用者との会話で中身を聞いているかもしれない。利用者が「こう書けば」と案を出したときは、その案が解答を知って出たものかを聞き、そうなら `trial --unblind` で回して分けて記録する。
- 一度に変えるのは 1 つ。1 回の結果で採否を決めない。
- 止める条件に当たったら、回さずに利用者に伝える。予算を超えて続けるか、目標を変えるかは、利用者が決める。

## 1. 始める前に

```sh
python3 tool/harnessmith.py check     # × があれば、harnessmith-setup に戻って先に通す
python3 tool/harnessmith.py status
```

`status` の最後が「止める:」なら、理由を伝えて止まる。

## 2. 回す

任せられているときは、止める条件までまとめて回す。時間がかかるので、バックグラウンドで実行する。

```sh
python3 tool/harnessmith.py auto --max-rounds 4
```

1 周は次のとおり。`auto` はこれを繰り返す。

1. 振り返り役が、採用中の構成の直近の試行から、変更を 1 つ入れた構成 `comp/g<世代>-<名前>/` と `HYPOTHESIS.md` を書く
2. 採点表にだけある言葉が入っていないかを機械で調べる。入っていたら、その案は捨てる
3. 候補を 2 回回して採点する
4. 候補と親を、試行の平均で比べる。どれかの部分がぶれの幅を超えて上がり、ぶれの幅を超えて下がった部分がなければ採用。それ以外は見送り
5. 採否と理由を台帳に書く

1 周ずつ確かめながら進めるときは、手で回す。

```sh
python3 tool/harnessmith.py reflect <試行のフォルダ> [親の構成]
python3 tool/harnessmith.py trial -c <候補> --parent <親> -n 2
python3 tool/harnessmith.py decide <候補> auto --parent <親>
```

## 3. 周が終わるたびに

- `status` を読み、採否と点を利用者に 2〜3 行で伝える。
- ベンチの変更（`comp/`、`notes/`、`ledger.jsonl`）を commit するかを、利用者の決まりに従って決める。頼まれていなければ commit しない。

## 4. 止まったとき

| 止まった理由 | すること |
| --- | --- |
| 目標に届いた | 採用中の構成、点（平均と幅）、使った額を伝える。「人に見せるときに添える 4 つ」（`METHOD.md`）を付ける |
| 改善のない世代が続いた | 構成をいじるのをやめる。採点表をもう一度 `audit` し、比べる相手の `--saw-answer` を確かめ直し、素の構成の回数を増やす。それでも測る側に誤りがなければ、いまの採用構成が到達点だと伝える。同じ方向で続けると利用者が決めたら `consult --note "<理由>"` を残してから回す |
| 予算 | 使った額と、次の 1 周の見込みを伝え、続けるかを聞く |
| 試行が採点されなかった | `leak.txt`（見てはいけないものに触れた）、`stderr.log`、時間切れを確かめる。構成の問題なら見送り、環境の問題なら直して回し直す |
| 振り返り役が「変えるところがない」と言った | `notes/` の理由を伝える。素の構成で十分、というのも結論である |

効かなかった案も、台帳と `notes/` に残っていること自体が成果になる。消さない。
